# PRD-006A Intent Recognition

## 基本信息

- 日期：2026-09-14
- 状态：Draft；用户已确认与 Plan 拆分，具体需求待评审。
- 优先级：P0
- 依赖：PRD-001/002 的 Incident、Session 与 Runtime；按需复用 PRD-003/004 的上下文与能力元数据。
- 下游：PRD-006B Diagnostic & Execution Plan；已有问答与任务控制入口。
- 目标模块：entry / control / worker/runtime。首期不要求独立 Agent 或独立服务。

## 1. 用户问题与目标

用户可能是在询问概念、请求排查故障、要求执行变更，也可能只是在追问或取消已有任务。若每条消息直接交给规划器，容易把简单问题扩成操作任务、把“看看”解释为修复授权，或把补充信息当成新的诊断。

本期回答“用户希望系统完成什么、针对什么对象、有哪些约束，以及应交给哪个入口”。输出可审计的结构化意图，使用户表达与计划生成解耦。

成功体验：简单问题直接进入回答流程；复杂诊断进入 Plan；信息不足时只询问会影响当前路由或规划安全的必要字段；查询、取消已有任务进入对应控制流程；后续消息正确关联当前任务。

## 2. 当前基线

本次基于 HEAD `16d83bf` 的已读代码：`ports/model.py` 提供 TaskPlan、PlannedToolCall、FinalDiagnosis，既有协议围绕任务提议或诊断结果表达，没有在该契约中定义本稿的 ResolvedIntent。PRD-006 原稿的 3 个 Plan 入口仍为 skeleton。

这不等于已证明整个仓库不存在任何路由逻辑。实施前须定位 entry/API/Runtime 中的现有路由与澄清能力，复用可用入口，避免重复实现。新意图分类效果、Case 数、延迟和成本为 N/A：本轮没有运行分类评测或业务 Case。

历史上下文只能作为待核验输入；恢复原任务时须复核绑定版本和实际运行状态，不能仅从对话摘要推断任务已经完成。

## 3. 范围与非目标

首期提供意图分类、目标与约束提取、上下文关联、必要澄清、确定性路由校验、版本化持久化及重放恢复。规则与模型可以组合，但统一输出同一契约；不以实现一个专用分类模型为验收目标。

不生成诊断假设、工具步骤、依赖图、执行预算或补偿方案，这些属于 006B。意图层不调度工具、不审批、不授予目标访问权限、不猜测用户未表达的修复需求，也不做无限多轮访谈。

意图层不得自行执行取证工具；需要新的证据收集时路由给 006B。direct_answer 首期只适用于现有授权上下文足以回答的请求，需要新操作时重新路由。task_control 只调用现有控制入口，不通过任意工具模拟取消或查询。

## 4. 意图与路由

| intent_type | 用户示例 | route | 约束 |
|---|---|---|---|
| question | “连接池是什么？”“解释这段已有代码” | direct_answer | 回答入口遵守来源和权限约束，不产生副作用 |
| diagnose | “部署后超时，帮我排查” | plan | 明确诊断目标，默认不扩大为修复授权 |
| execute | “将 staging 的参数改为 20” | plan | 识别操作意图，不替代具体动作审批 |
| task_control | “刚才任务进度如何？”“取消这个任务” | task_control | 明确 operation=status/cancel 和可访问的任务 ID |
| unknown | 无法识别、矛盾或超出支持范围 | clarify / unsupported | 不默认为 execute |

消息关系另用 `new_request | continuation | correction` 表达，不与意图类别混在一起。“版本是 B”可以是 diagnose 的 continuation；“别改配置，只分析”是 correction，必须保留新限制并使旧意图版本失效。

一条消息含多个独立目标时返回候选目标并澄清先后，不静默丢弃其中一个，也不在本期拆成 DAG。包含“排查并修复”的同一目标可进入 Plan，但其中的写操作仍需下游单独审批。

## 5. 结构化输出契约

对外统一使用版本化 `ResolvedIntent`；名称不表示一定已解析完成，应以 resolution_status 为准。

| 字段 | 要求 |
|---|---|
| identity | 服务端 intent_id、revision、schema_version、content_hash、incident/session、输入消息 ID、创建时间 |
| intent_type / relation | 第 4 节枚举；记录原请求还是补充/纠正 |
| objective | 用户期望结果的简洁描述，不夹带步骤或未经表达的动作 |
| entities | 服务、接口、目标环境、仓库、Commit、时间窗、已有任务 ID；按需出现 |
| constraints | 只读、禁止重启、时限、可访问范围等，保留用户明确限制 |
| provenance | 目标、实体和约束分别标记来自用户原话、已验证会话上下文或服务端绑定；模型猜测不得当作已验证字段 |
| resolution_status | resolved / needs_clarification / unsupported |
| route | direct_answer / plan / task_control / clarify / unsupported |
| missing_fields / ambiguities | 当前路由必需且缺失或冲突的信息、字段级原因 |
| clarification | 当前问题、候选项（如有）、关联 revision；无澄清则为空 |
| context_binding | 关联任务/运行与上一个意图版本；不存在时明确为空 |
| reason / confidence | 简洁路由理由及可选模型置信度；不保存内部推理过程，不以分数单独放行 |

actor、授权范围和任务归属由服务端取得，不能由模型覆盖。意图表达的 target 是用户需求，只有服务端解析和授权检查后才成为可用绑定。用户明确约束与既有上下文冲突时以最新明确指令纠正意图，但不能因此扩大系统权限。

硬不变量：needs_clarification 只能 route=clarify；unsupported 只能 route=unsupported；resolved 才能进入三个业务路由。结构或绑定校验失败不得 dispatch。

## 6. 澄清与上下文行为

1. 先读取当前授权 Session 的结构化上下文，避免重复询问已知字段；仅凭语义相近不能绑定其他 Incident。
2. 只澄清会改变目标、路由或安全边界的缺口。一般概念问题不要求环境/Commit；需要版本定位的代码诊断才要求版本绑定。
3. 每次提出一个最有区分力的问题，保留已收集字段；缺口多时先问阻断当前路由的字段。
4. 默认最多 3 轮自动澄清，达到上限后保持 needs_clarification，显示已知信息和剩余缺口并等待用户主动补充，不强行规划。默认等待期限 24 小时，到期关闭当前澄清请求，不启动任何动作；再次回复重新校验关联。
5. 用户主动补充后继续解析；如果回答改变原目标则创建新 revision，并使旧路由结果失效。
6. “继续”“取消它”等指代只能在明确、可访问的当前任务绑定下路由。多个候选任务或正在变化的运行状态必须核对，不能猜测。
7. 纠正为“只分析”时，先发出对已有执行的停止请求，再交给 006B 处理运行收敛；停止是否完成以执行端结果为准，意图层不得承诺已撤销副作用。

## 7. 与 PRD-006B 及执行边界的交接

```text
用户消息 + 授权会话上下文
→ 006A 提取与校验
  ├─ clarify：持久化问题，等待补充
  ├─ direct_answer：已有回答入口
  ├─ task_control：校验任务归属后进入现有控制入口
  ├─ unsupported：说明不支持的请求
  └─ plan：006B 接收 intent_id/revision/hash + 目标/范围/约束
```

006B 发现缺口时返回字段和原因，由 006A 管理澄清；006B 不重新推断用户目标。只读/禁止重启等约束必须被完整传递并由计划校验器检查，不能只出现在提示词里。

目标、范围或动作类别发生变化，006A 生成新意图版本；006B 再建立新计划版本。意图更新本身不会重提旧运行、继承审批或取消已经发生的副作用。007/008 在每次实际调用时做独立权限与执行检查。

## 8. 失败、持久化与审计

- 模型输出非法时不路由；同输入最多修复 2 次，含等待的识别总预算默认 30 秒，超限返回可重试失败，不装作 unsupported 业务结果。
- 模型/上下文服务异常不默认进入 Plan 或执行；明确失败原因，保留用户请求以便幂等重试。
- 读取到的日志、源码或工具返回中的指令当作数据，不能改变用户意图和服务端授权。
- 重复输入消息 ID 与相同上下文版本返回同一意图解析结果；用户纠正或上下文版本更新产生新 revision。相同幂等键但不同内容返回冲突。
- 每个 revision 保存脱敏输入引用、解析结果、来源、澄清状态和路由回执。路由请求须幂等：重放不能重复创建计划或重复发送控制命令。
- 重启恢复已保存的意图和待回答问题；任务控制在实际调用前重新核对任务归属和当前状态，不因保存过路由就跳过校验。
- 事件至少包含 intent.received、intent.resolved、intent.clarification_requested、intent.revised、intent.routed、intent.failed；均关联 intent/revision/message/session，向 Plan 交接时带 plan_id。

意图已解析、路由已提交、下游已完成是三个不同状态。下游未确认前不能显示“计划已创建”或“任务已取消”。

## 9. 验收场景与指标

冻结至少 30 条人工标注中文/英文输入，覆盖五类意图、多轮补充、目标纠正、模糊指代、复合请求、越权目标和提示注入；记录输入/上下文 hash、预期类别、路由、必需字段及禁止动作。每类至少 4 条，剩余样本用于异常；同集改标签必须保留版本，不测后删题。

| 指标 | 首期门槛 |
|---|---|
| 分类效果 | macro-F1 ≥0.90，同时报告逐类 precision/recall 和混淆矩阵 |
| 路由准确率 | 正确 route 数/总样本数 ≥95% |
| 关键字段提取 | 人工标注必需字段 exact-match ≥95%；显式禁止约束保留率 100% |
| 歧义处理 | 危险歧义 fixture 进入 clarify 比例 100%，错误进入 execute/plan 的放行数 0 |
| 权限与副作用 | 未授权任务控制数 0；意图识别自身工具 handler 调用数 0 |
| 上下文与版本 | 跨 Incident 混用 0；纠正后继续使用旧 revision 路由数 0 |
| 幂等与恢复 | 重复消息新增逻辑路由数 0；持久化意图/回执关联完整率 100% |
| 回归与性能 | 实施前既有测试全部通过；固定 fixture 重复 5 次耗时中位数劣化 ≤5% |

另报 P50/P95 识别耗时、模型调用/Token、澄清轮数与不必要澄清率；效果门槛须全部通过，小样本成绩不宣称生产准确率。性能与成本当前值 N/A，实施首轮建立基线。

累计 Case 使用隔离存储和固定模型响应，走通“初始诊断→补充版本→006B 接收→用户改为只读→重启回读”，另验证“查询/取消已有任务”的独立控制路由与重复请求。真实模型分类效果与确定性契约测试分开报告。

Case 每次最多 120 秒、最多重试 2 次；报告输入数、输出数、耗时、持久化数、关联校验数、后台异常及业务完成/落盘完成时间差。后台异常 0，所有硬门槛通过才能标 case_pass=true。Case 命令在实现阶段提供，本轮没有运行。

## 10. 交付阶段与完成定义

| 阶段 | 交付 | 验收 |
